## 0. 阅读方式与开发约定

每页按以下顺序开发：

1. 先按“首屏加载”完成读接口和页面状态。
2. 再按“控件—接口矩阵”逐个实现按钮。
3. 后端先完成 schema、路由和状态码，再实现 service/repository。
4. 前端只调用 `src/api` 中的强类型函数，不在组件内拼 URL。
5. 最后按“页面验收”编写 E2E。

UI ID 命名：`Pxx-区域-动作`，例如 `P05-FILTER-RUN`。测试优先使用 `data-testid="P05-FILTER-RUN"`，不要依赖中文按钮文本定位。

接口均省略共同前缀 `/api/v1`。统一响应、错误、分页、异步任务和枚举见总方案第 5 章。

### 0.1 前端请求规范

```ts
export interface ApiEnvelope<T> {
  code: string
  message: string
  data: T
  request_id: string
  server_time: string
}

export interface AsyncAccepted {
  job_id: string
  resource_id: string
  status: 'queued'
  poll_url: string
}
```

- GET 查询切换时取消上一个相同资源请求，避免旧响应覆盖新筛选。
- 仅对网络错误和 502/503 的 GET 自动重试两次，退避 300ms/900ms；POST 不自动重试，使用幂等键由用户点击重试。
- 所有错误 Toast 显示简短中文原因，详情区域显示 `request_id` 和“复制”按钮。
- 删除、关闭、启用模型、发布数据必须使用确认弹窗；弹窗确认键在请求期间禁用。

### 0.2 后端路由模板

```python
@router.post(
    "/predictions",
    status_code=status.HTTP_202_ACCEPTED,
    response_model=ApiEnvelope[AsyncAccepted],
)
def create_prediction(
    body: PredictionCreate,
    idempotency_key: Annotated[str, Header(alias="Idempotency-Key")],
    user: CurrentUser,
    service: PredictionServiceDep,
):
    return service.submit(body, user, idempotency_key)
```

路由只做鉴权、schema 校验、service 调用和响应映射；事务、状态机和算法调用都放 service。

### 0.3 共享接口

| 接口 | 用途 | 关键返回 |
|---|---|---|
| `GET /health` | 启动检查 | `status`, `db`, `model_mode`, `version` |
| `GET /metadata` | 全局字典 | metrics、风险等级、预测尺度、站点类型 |
| `GET /jobs/{job_id}` | 异步任务轮询 | status、progress、step、error、resource_url |
| `POST /jobs/{job_id}/cancel` | 取消允许取消的任务 | 200 新状态；已完成返回 409 |
| `WS /ws/v1/events?token=` | 任务/预警事件 | `job.progress`, `job.completed`, `warning.created` |
| `GET /exports/{token}` | 下载导出文件 | 文件流；过期返回 410 |

### 0.4 风险状态机

```text
new → acknowledged → processing → resolved → closed
  └──────────────────────────────→ closed（误报，需说明）
acknowledged/processing/resolved → new 不允许
closed 不允许修改，只允许查看审计记录
```

状态更新请求必须带当前 `version`。版本不一致返回 409 `VERSION_CONFLICT`，前端重新加载详情并提示“该预警已被其他人更新”。

### P01.4 后端实现

- `CockpitService.get_snapshot()` 在一个数据库只读事务中确定 `as_of`，随后所有查询使用该时间。
- 网格不在请求中临时训练/插值；由风险任务预计算并按 `as_of+stage+metric` 查询。
- 快照缓存键包含湖区、metric、stage、data_version；TTL 30 秒，预警创建时主动失效。
- 站点 summary 的 `factors` 来自最近成功预测解释；没有则返回空数组和 `explanation_available=false`，禁止伪造。

### P01.5 验收

- 首屏不操作即可回答“当前最高风险站点、最大风险概率、预警数”。
- 点击排行与点击 3D 浮标选中同一站点，URL 可复制复现。
- 拖动时间轴 3D 网格、粒子、KPI 的 `as_of` 同步；不得出现时刻混用。
- 连续进入/离开页面 20 次，GPU memory 不持续增长。
- WebSocket 断开后出现黄色状态并自动轮询，核心页面仍可用。

### P02.4 后端流水线

1. 上传隔离区保存并计算 SHA-256；相同 source+checksum 返回已有任务。
2. 解析阶段只读原始文件，禁止覆盖。
3. 按映射 profile 转标准字段和单位。
4. 规则质控：缺失、范围、单位、重复、时间逆序、坐标越界。
5. 时间对齐到小时/日，空间匹配到站点/网格。
6. 结果进入 staging 表；只有用户点击发布才写 observation 正式表。
7. 发布事务要么全部成功，要么全部回滚；生成新 `dataset_version`。

### P02.5 验收

- 可上传一个 100—500 行样例，看到每阶段计数和问题行。
- 阻断问题未解决时“发布”返回明确原因；修正后可成功入库。
- 原始文件、标准数据、质控报告能通过同一 job_id 追踪。
- 页面明确区分 observed/remote_sensed/interpolated/simulated。

### P06.4 解释规则

- waterfall 的贡献单位与输出单位一致；分类风险可使用 log-odds，但 UI 必须说明并提供概率视图。
- `base + Σ contribution ≈ output` 后端校验，超容差则任务失败，不返回自相矛盾解释。
- 全局解释注明数据范围、样本数和背景集；局部解释注明 target_at。
- 自动文字说明只引用 factors 中的证据，不得生成不存在的因果结论；统一使用“提高/降低预测值”，不写成已证明因果。

- 模型/时点切换后旧图不会短暂冒充新结果。
- 报告包含模型版本、数据版本、解释方法和 provenance。

### P08.4 后端状态与事务

- `WarningService.transition()` 在一个事务内：锁定预警/检查 version→校验状态机→写 warning_action→更新主表→写 audit→发布事件。
- 自动创建预警的去重键：target+metric+forecast window+level bucket；风险升级可更新现有 active 事件并留痕，不刷屏新建。
- 推送模板只使用允许字段；模拟发送也要存 payload、recipients、mode 和 result。
- 关闭后不物理删除；附件以哈希校验完整性。

### P08.5 验收

- 能完成 new→acknowledged→processing→resolved→closed 全流程。
- 任何一步刷新页面，状态、负责人、措施和时间线均可恢复。
- 两个浏览器同时操作时，后提交者收到版本冲突而不是覆盖。
- 导出处置单可追溯到预测、解释、预案、推送和操作者。

### P09.4 质量门槛与上线

- 模型只有 `succeeded run + frozen test evaluation + artifact checksum + schema compatibility` 才可 validated。
- activate 是事务性指针切换，不覆盖旧工件；缓存和工作进程收到 `model.activated` 后热加载，新请求使用新版本，已运行任务继续旧版本。
- 回滚指向历史已验证工件，不重新训练。
- 指标页面默认只比较相同 dataset_version、测试窗、目标和尺度；不满足时展示“不可比”，禁止画误导性排行榜。

### P09.5 验收

- 每个指标能追溯到数据集、测试区间、随机种子和运行 ID。
- 训练失败保留日志和参数，可从失败配置复跑。
- 启用后新预测固定使用新 active 版本；旧 prediction 仍显示原版本。
- 回滚后健康检查和一条 smoke prediction 通过才标记 deployment 成功。

## 15. 联调交付顺序

1. 后端发布 `/metadata` 和全部 Pydantic schema 示例；前端生成 TS 类型。
2. 各接口先返回契约稳定的确定性数据，所有响应带 provenance。
3. 前端实现状态、按钮和 E2E，不等待真实模型。
4. 后端逐个替换 repository 和算法实现，保持 schema 不变。
5. 算法线以固定 `PredictionInput/Output` 交付；禁止只交 Notebook/Excel。
6. 每日跑契约测试和主线 E2E；任何字段变更先改文档、OpenAPI、类型，再改实现。

完成标准不是“页面能打开”，而是九页之间的业务对象 ID 可以贯通：

```text
dataset_version
  → inversion_id / model_id
  → prediction_id
  → explanation_id / simulation_id / frame_id
  → warning_id
  → plan_id / action_id / push_id / audit_id
```

当这条链能从页面点击、接口响应、数据库记录和导出报告四个角度互相核对时，前后端开发才算完整。
