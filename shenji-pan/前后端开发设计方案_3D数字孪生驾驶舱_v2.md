# 前后端开发设计方案 v2.0 — 3D 数字孪生驾驶舱

> 制定日期：2026-08-07
> 对应赛题：A23 · 基于机理和AI融合的地表水蓝藻水华监测预警模型设计与实现
> 定位：赛题第四模块「数字孪生与可视化预警」的核心载体，同时也是整个演示的门面
> 已确认决策：3D 引擎 = **three.js 自建太湖沙盘**（离线可用、风格统一）；后端数据层 = **SQLite 起步**（零安装、真持久化，SQLAlchemy 抽象后最后可切 PostgreSQL）
> 组织方式：**算法线 与 前后端线 完全解耦并行**——前后端开发期间算法先用「确定性占位模型」，接口契约冻结，最后整体替换为真实机理+AI 模型

---

## 1. 设计原则（本方案的基础）

1. **两线并行、契约冻结**：算法线（机理+AI+融合+SHAP）与前后端线互不阻塞。前后端只依赖 `ml/` 层暴露的**接口签名**，不依赖实现。算法线完成后替换 `ml/` 层实现，前端零改动。
2. **占位算法 ≠ random**：占位模型是**确定性规则模型**（同一输入永远同一输出），并且数值有"剧情"（7 月升温 → 藻华抬头 → 降雨回落），保证演示可复现、可讲故事的底线；到替换日之前，系统整体始终可演示。
3. **3D 是门面，2D 是主力**：3D 场景负责"震撼感"（答辩第一印象），现有的 2D 页面（站点研判、SHAP、预警列表）负责"信息密度"（答辩细节），两者共用同一份 state 联动。
4. **借鉴已调研项目**：形态参考「水脉卫士」（FastAPI+Vue3+大屏+预测+预警闭环）与 B站数字孪生智慧水利；3D 实现参考 three.js 官方生态；太湖数据场景参考 WQMFS / 太湖公开数据集。
5. **答辩环境自保**：全部资源本地化/离线化（three.js 无外部纹理依赖、接口全部本地后端），断网也能完整演示。

### 3.2 3D 场景构成（ThreeLakeScene.vue）

> 暗色科技风，与现有设计系统（tokens.css 的蓝黑玻璃风格）统一。

| 场景元素 | 实现 | 数据来源 | 视觉效果 |
|---|---|---|---|
| **背景** | 场景渐变色 + 星星点 | 静态 | 深空科技感 |
| **太湖水面** | `PlaneGeometry`（~64×64 分段）+ 半透明深蓝材质 + **顶点正弦波动画** | 静态 | 真实水域感，全离线 |
| **站点浮标 ×8** | 发光球体/圆环 + `CylinderGeometry` 半透明光柱 | `/api/sites` | 光柱颜色 = 风险等级（红/橙/绿），高站高低光柱，低风险低光柱 |
| **风险热力网格** | 11×19 `PlaneGeometry` 平面悬浮水面上，顶点/纹理按 `risk_value` 着色 | `/api/map/risk`（带 stage） | 档位切换时**网格颜色渐变扩散/消退**（赛题"推演"直观呈现） |
| **水华扩散粒子** | `Points`（≤5000）+ BufferGeometry + 缓动动画 | `/api/timeline`（stage 预演序列） | 时间轴播放时粒子从站点向外扩散，模拟水华蔓延 |
| **预警光柱** | 高风险站点的脉冲光柱 + 扩散圆环（scale 动画） | `/api/warnings` | 预警现场感 |
| **相机** | PerspectiveCamera + OrbitControls（自动慢旋转） | — | 点击站点 → 相机 tween 聚焦该站 |

### 3.3 3D 与现有系统的联动（关键设计）

```
cockpit store（stageKey / selectedPoint / playing / speed，URL 同步）
        ▲
        │ 双向联动
        ▼
ThreeLakeScene.vue
  ├─ stageKey 变化 → 热力网格顶点色插值过渡（0.8s）+ 粒子分布重排
  ├─ selectedPoint 变化 → 相机聚焦 + 该站光柱高亮
  ├─ playing 播放 → 粒子扩散动画 / 网格随时间档演进
  └─ 3D 点击站点（raycaster）→ 写回 store.selectedPoint → 2D 页面同步高亮
```

**联动复用的关键资产（已存在，无需重写）**：
- `stores/cockpit.js`：五档切换、点位选择、播放状态、URL 双向同步
- `TimeAxisBar.vue`：时间轴播放器直接嵌入 3D 页面
- `services/api.js`：站点/热力/预警/预测接口 + mock 降级
- `EChart.vue` + echartsTheme.js：3D 页面左右面板的图表直接复用

## 4. 后端设计

### 4.1 分层结构（对齐规划文档，落地为代码）

```
backend/
├─ main.py                # 入口：注册路由/中间件/启动任务
├─ core/                  # settings.py（pydantic-settings）、db.py（SQLAlchemy+SQLite）、log.py
├─ models/                # ORM 12 张表（先建核心 8 张，观测表合并建）
├─ schemas/               # Pydantic v2 契约（与接口文档一一对应）
├─ routers/               # 17 个接口路由（薄层）
├─ services/              # predict / explain / warning / ingest / plan
├─ tasks/                 # APScheduler 定时任务（预警自动生成）
├─ ml/                    # 算法层：4 个模块，接口抽象 + 占位实现（§4.4）
├─ seed.py                # 种子数据生成脚本（有剧情的 30 天数据）
├─ app.db                 # SQLite 文件库（运行时生成）
└─ requirements.txt
```

### 4.2 数据库（SQLite 起步）

- SQLAlchemy 2.x + `sqlite:///app.db`，**零安装零配置**
- 12 张表设计保留，实施时优先核心 8 张：`station / water_quality_obs / weather_obs / hydrology_obs / prediction / explanation / warning_event / emergency_plan`（remote_sensing_cell、model_registry、warning_push_log、ingest_job 第二批）
- 观测表数据量：8 站 × 30 天 × 逐小时 ≈ 5,760 行/表，SQLite 毫无压力
- 种子数据 = `seed.py` 生成并入库：chla 5~80 μg/L、水温 18~33℃、TP 0.02~0.15 mg/L，**有"7 月中旬升温→藻华抬头→一次降雨回落"的剧情**，站点坐标全部太湖化（S001~S008）
- 最后交付阶段补 docker-compose（PostgreSQL+PostGIS）作为部署说明材料，代码通过 SQLAlchemy 方言切换即可，前端无感知

### 4.4 算法占位策略（核心机制，前后端线解耦的关键）

```
ml/ 每个模块 = 接口抽象（类/函数签名固定）+ 实现可切换

config 开关：MODEL_MODE = "placeholder" | "real"（env 或 settings）
services 层调用：get_mechanism() → 返回占位或真实实现
```

**占位实现要求（对比现在的 random mock 是本质升级）：**

| 要求 | 现在的 random mock | 占位模型（新） |
|---|---|---|
| 确定性 | ❌ 每次刷新变 | ✅ 同输入同输出（可复现演示） |
| 剧情 | ❌ 无逻辑 | ✅ 温度↑→叶绿素↑、降雨→回落、站点差异 |
| 参数 | ❌ 无 | ✅ 有真实可调参数（增长率/半饱和/基底值），可讲"参数" |
| 指标 | ❌ random 编 | ✅ R²/RMSE 由占位模型在种子数据上真实计算（如实标注"占位基线"） |
| 替换 | — | ✅ 算法线完成后 `MODEL_MODE=real` 即切换，接口/前端零改动 |

占位模型示例（机理）：`chla(t+1) = chla(t) · (1 + r(T,TP)) − 沉降`，r 由水温正弦、TP 线性组合——**规则虽简单，但与真实机理模型的输入输出同构**，前端/数据库/服务层全部按最终形态开发。
