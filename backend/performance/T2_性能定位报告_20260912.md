## 2. 调用链分析（读路径完整链）

```

             └ _runtime_imports()

```

**耗时环节假设清单（开工时列出，测量后标注）**：
- H1 single-flight 惊群未挡住 → **排除**（日志证实同波仅 1 个 builder，其余 19 个 waiter 等待后命中）。
- H2 每请求 `algorithm.status()` 重复计算 → **证实（根因 B）**。
- H3 压测撞上后台预热/重生成窗口 → **证实（根因 A，基线压测 FAIL 的主因）**。
- H4 20×270KB 响应序列化（pydantic 校验+JSON dumps）GIL 串行 → 存在但占比小（估 8-10ms/请求，修后命中波已 ~90ms，不值得为此跨 3 文件改造）。
- H5 MEE provider.status() 慢 → 排除（1-10ms）。
- H6 快照组装（assemble×7）本身慢 → 空闲时 ~100-200ms，非主因；仅在被预热线程饿死时放大（1200-1650ms）。

- 工具：`backend/performance/probe_snapshot.py`（`backend/.venv` python，urllib + 线程）。

## 4. 根因结论（证据）

### 根因 A：基线压测 C1/C2 是在后端启动/换代重生成窗口内跑的（主因，环境因素）
- 时序证据：8000 后端进程启动 **15:48:07**，stress-report.json `started_at=15:48:10.707Z(+0800)`——压测在后端启动 **3.7 秒后**开跑。
- 启动时磁盘最新快照代（09-12T06:54Z 采集代）落后实测源 → 版本键变化 → 后台线程全量重生成：文件 mtime 显示该重生成从 15:48 持续到 **15:57:08**（15:55:22 阶段1 完成、15:57:08 站点层完成），C1 五波（15:48:40-49）全程落在窗口内。
- 窗口内容：全湖 7 时效推理 + 解释预热（重启/换代后 35 次 `predict_suite`，实测 40-60s、200% CPU）+ 79 站×7 时效批量推理 + **每批 19.5MB stations.json 全量序列化落盘 ×3**。全部与请求处理在单 worker（uvicorn 无 --workers）的 GIL 上竞争。
- 主动复现（18:30 重启后立即探针）：预热窗口内 20 并发首波 **1530-1973ms**、后续波 **405-868ms**——与基线报告"首波全 ~2700+ / 550-800 / 280-620"的阶梯形态一致；当前代码与压测时代码完全相同（git 核对），排除"ec37ddf single-flight 引入阶梯"的怀疑——**阶梯是预热线程 CPU 竞争的投影，不是缓存锁排队**。
- 量级差异解释：基线压测撞的是全量重生成峰值（推理+预热+落盘），复现撞的是解释预热段，故 2700 vs 1973。

### 根因 B：每请求重复计算 `algorithm.status()`（稳态地板，已修复）
- 服务端计时（空闲后台）：命中路径 total≈serving_current，其中 **algo_status 单线程 ~30ms/次**，20 并发下 GIL 串行放大为 **138-190ms/请求，占命中路径总耗时 ~80%**。
- 代码缺陷：`__init__` 已声明 `self._algorithm_status_cache` 与 `ALGORITHM_STATUS_TTL_S = 2.0`，但 `_algorithm_status()` 从未使用它们（遗留的未完成接线）。
- C2 八站并发的 746-856ms（修前空闲）中绝大部分同样是 8 个 builder/hit 各自跑 status() 的串行放大。

## 5. 修复内容与前后对比

### 修复（最小、克制，均在 T2 文件边界内）
1. **`_algorithm_status()` 接线 2s TTL 缓存**：并发突发内只算一次 `algorithm.status()`；版本键对模型产物变化的感知延迟上限 2s ≪ 30s 轮询周期，无正确性影响。未加新锁（幂等重算无竞态危害）。
2. **可选计时探针**（`TAIHU_SNAPSHOT_TIMING=1`，默认关闭零开销）：记录每请求 serving_current/realtime/algo_status/hit/build 分段到 `backend/performance/snapshot_timing.log`。
3. **压测预热守卫**（stress-heatmap.mjs）：开压前等待后端度过预热窗口，防止阶段 3 复跑再被环境因素污染。

## 6. 残余风险与未做项（如实披露）

1. **每代 MEE 采集后的 ~90-130s 重生成窗口依旧存在**（架构性：后台线程与请求共享单 worker GIL）。本次修复不减少该窗口 CPU 总量，只保证读路径不重复计算。压测/演示须避开窗口；stress-heatmap.mjs 已内置守卫。
2. **30s 巡检的间歇 CPU 尖峰**：`ensure_fresh → _ensure_stations_complete → _station_scope → realtime.stations(active='latest')` 每轮对 79 站做 observations DataFrame 全表过滤（parquet 持续增长会越来越贵）。未修（在 providers.py，超出本次边界），见台账建议 L-perf-04。
3. 响应预序列化（envelope data 复用一次 JSON 字节）未做：修后命中波已 ~90ms，该优化收益边际小、需跨 api.py/services.py 改动，按"最小修复"纪律放弃。
4. `dist_check_w1/w2` 等历史遗留与本任务无关，未触碰。
